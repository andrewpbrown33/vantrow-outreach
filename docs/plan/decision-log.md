| 2026-08-10 | **WORKSTREAM C: product surfaces built on the deck v2.1 contract — and a stranding bug found in the draft→start flow** | The three read surfaces (Activity home, Sequences overview, Sequence detail) plus **create-sequence** and **import-prospects** now run on real rows, so operating Nudgerow no longer means opening the SQL editor. Building the create→import→start path **surfaced a real defect in merged engine behaviour**: the sweep parks an enrollment whose sequence is not active (`pause_reason = 'sequence not active'`) and **clears `next_touch_at`** — correct, since nothing should be armed while a sequence is off, but `next_touch_at` IS the schedule (Gate 5), and `resumeDueOoo` only revives `'out of office'`. Regression-tested against real Postgres and **mutation-checked** (disabling the revival fails the test). Same lesson as the Gmail Message-ID bug: the hole was in the seam between two correct components, and only a real-substrate test found it. | Claude |
| 2026-08-10 | **SIGN-IN: Supabase Auth magic link driven server-side (PKCE), own signed session cookie — no client SDK, no `NEXT_PUBLIC_*`, no new dependencies** | The platform app is on a public URL with real prospect data, so the surfaces needed auth. | 2026-08-09 | **B3 CORRECTION: Gmail rewrites Message-ID — touch identity moves to a custom header + SENT-label recovery** | The first live send (dogfood mailbox, real Gmail) **found a correctness bug in merged code**: B3's design made the RFC822 `Message-ID` the touch identity (`<touch-{enrollment}-{step}@domain>`), but **Gmail replaces that header on send** (observed: `<CAK71HS6…@mail.gmail.com>`). Consequences, both proven live: `rfc822msgid:` lookups always missed, so `checkSent` said "not sent" about a message that HAD gone out and the retry **sent a duplicate** — precisely the failure I1/I8 exist to prevent; and inbound replies quote *Gmail's* id in `In-Reply-To`, which nothing in the schema could resolve to a touch. **Fix:** identity rides `X-Nudgerow-Key` (a custom header, which Gmail preserves); recovery scans the **SENT label index**, which is immediately consistent — Gmail's *search* index lagged minutes behind in testing and is unusable for a crash-recovery check that must answer now; scans are bounded and run only on retries (epoch > 0), so steady-state sends stay one API call. The provider now returns Gmail's own `threadId` + `rfc822MessageId`, persisted by migration **0004** into `touch_ledger`, and both threading and inbound reply-matching key off those stored provider ids (sender-address matching remains the fallback). Old provider tests asserted the broken behavior and passed while production duplicated — replaced with a fake Gmail that **rewrites Message-ID like the real one**, including an explicit duplicate-send regression test. Verified end-to-end against live Gmail: one message on the wire, `checkSent` true, retry recovers the same id. Lesson recorded for the seam: **never let a provider-owned field carry our identity.** | Claude (live-dogfood finding) |
